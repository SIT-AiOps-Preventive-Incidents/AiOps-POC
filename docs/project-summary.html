สรุปสั้นๆ

  • เครื่องมีแรงไม่พอสำหรับ Kubernetes เลยใช้ Docker Compose แทน แต่ยังแบ่งเป็น 4 ส่วนเหมือน namespace ในสไลด์ (app, obs, agentic-ai และฝั่งลูกค้า)
  • ใช้ LLM ตัวเล็ก qwen2.5:1.5b รันบน CPU ผ่าน Ollama จำกัดไว้ 3 cores ไม่ให้แย่ง CPU จาก service อื่น
  • ทำ demo shop 4 services (frontend, checkout, payment, inventory) ที่ใส่ OpenTelemetry แล้ว และมี loadgen ยิง traffic ตลอด เอาไว้ inject fault ตอน demo
  • ทุก request วิ่งผ่าน firewall → load balancer → frontend 2 instances ก่อนจะถึง checkout, payment และ inventory ทุก hop ถูก trace ไว้ ดูได้จากหน้า Service Map
  • Agent ใช้ log ของ firewall และ load balancer เป็น evidence ด้วย จึงแยกได้ว่าพังที่ instance เดียวหรือพังทั้ง service
  • ทุกวิธีแก้ต้อง dry run ก่อนเสมอ และจะทำจริงก็ต่อเมื่อ owner ของ service กด approve แล้ว ก่อนลงมือระบบจะ dry run ซ้ำอีกรอบ
  • ผลทดสอบ end-to-end อยู่ในหัวข้อผลทดสอบด้านล่าง

Architecture

ทุกอย่างอยู่บน Docker host เครื่องเดียว เส้นทึบคือ data ที่ไหลเข้า ส่วนเส้นประสีแดงคือ action ที่ระบบไปแก้ฝั่งลูกค้า ซึ่งจะเกิดขึ้นหลังจากคนกด approve เท่านั้น

Customer environment

ระบบของลูกค้าที่เราเข้าไปดูแล ตอนนี้เป็น demo shop ที่ส่ง traces และ logs ผ่าน OTLP ส่วน host ส่ง metrics ผ่าน node-exporter ลูกค้าจริงจะต่อเข้ามาผ่านหน้า Connect App และ Connect Infrastructure

obs

Collector แปลง traces เป็น request rate, error rate และ latency แล้วแยก label ตาม version กับ commit ทำให้รู้ว่า error มาจาก commit ไหน ข้อมูลเก็บไว้ใน Prometheus, Loki และ Tempo

agentic-ai

Detector หา anomaly แล้ว orchestrator เลือก skill ซึ่งแต่ละ skill เรียกได้เฉพาะ tool แบบ read-only จากนั้น LLM สรุปผล โดยมี guard คอยเช็คว่าคำตอบตรงกับ evidence

app

หน้าเว็บสไตล์ Dynatrace ที่ใช้ connect, ดู problem และ approve รวมถึงตัว executor ที่รันได้แค่ action ใน allow-list และจะรันหลังมีคน approve แล้วเท่านั้น

ความสอดคล้องกับโครงงาน

  • C1 Late detection: detector ทุก 15 วินาที ใช้ adaptive baseline วัดได้ว่า detect ภายใน 35–50 วินาที
  • C2 Scattered telemetry: metrics, logs, traces, log ของ firewall/LB และ deploy history รวมอยู่ใน obs stack เดียว ผูกกันด้วย trace_id
  • C3 Manual RCA: agent ทำ RCA เสร็จใน 1–2 นาที ถ้าเคยเจอ pattern นี้แล้วใช้ 23 วินาที
  • C4 Hidden change impact: ทุก span มี app.version / app.commit และ CI ส่ง deploy event เข้ามา
  • C5 Multi-team handoffs: หน้า Problem เดียวมีทั้ง RCA, dry run และ owner approve พร้อมแจ้ง Teams ไปที่ owner
  • C6 Growing toil: runbook memory + scoring · ตาม OUT scope คือไม่แก้ source code และไม่ทำงานเองโดยไม่มีคนอนุมัติ
  • Resource: Docker Compose แทน K8s · LLM 1.5B บน CPU · ทุก container มี memory limit · ตอนปกติใช้ CPU ราว 4% และ RAM ราว 20%

Dry run ก่อนแก้ทุกครั้ง

Agent จะไม่เปลี่ยนอะไรในระบบเองเลย ทุกวิธีแก้ที่เสนอต้องผ่านการ dry run ซึ่งเป็นการเช็คแบบ read-only ว่าทำได้จริงไหม จะเปลี่ยนอะไรบ้าง และกระทบใครบ้าง วิธีไหนที่ dry run ไม่ผ่านจะกด approve ไม่ได้

ที่ต้องมีขั้นนี้เพราะเจอเคสจริงตอนทดสอบ มีคนกด inject bad deploy ซ้ำ 2 ครั้ง payment เลยมี v1.3.0 ที่พัง 2 commit ติดกัน เวอร์ชันแรกของ agent เลือก rollback ไป "deploy ก่อนหน้า" ซึ่งก็คือ v1.3.0 อีกตัวที่พังเหมือนกัน ตอนนี้ agent จะเลือก build ล่าสุดที่ไม่ได้อยู่ในกลุ่มที่พัง และ dry run จะเช็คซ้ำจาก metrics ว่า build นั้นดีจริง

Service Map

หน้า Service Map ใน Web app วาดทุก hop ที่ request วิ่งผ่าน แบ่งเป็นชั้น Clients → Perimeter (firewall) → Load balancing → Web tier (แยกเป็นราย instance) → App tier → Backend แต่ละ node แสดง req/s, error % และ p95 ส่วนเส้นแสดง req/s และสัดส่วนที่ LB แบ่งไปแต่ละ instance node ที่มี problem จะเป็นสีแดง กดแล้วจะไปที่หน้า problem นั้น

เส้นเชื่อม (ใครเรียกใคร) มาจาก parent/child span ใน trace ที่สุ่มมาจาก Tempo ส่วนตัวเลข rate มาจาก span metrics ใน Prometheus

Rollback ไปหา build ที่พังอีกตัว

ตอนกด inject ซ้ำ 2 ครั้ง agent เลือก rollback ไป "deploy ก่อนหน้า" ซึ่งก็พังเหมือนกัน วิธีแก้คือเพิ่มการ dry run ที่เช็คจาก metrics ย้อนหลัง 24 ชม. ว่า build เป้าหมายดีจริง ตอนนี้ agent ไล่ deploy history หา build ล่าสุดที่ผ่านเกณฑ์ และในการทดสอบรอบหลัง dry run ก็จับ target ที่ไม่ดีได้จริง

Verify เร็วไปจนนับ error ช่วงที่กำลัง restart

Restart instance ใช้เวลาราว 8 วินาที LB ยังส่ง request ไปหา instance นั้นอยู่ ทำให้ 502 ค้างอยู่ใน window 1 นาทีตอนเช็ค วิธีแก้มี 2 ส่วน ส่วนแรกตั้ง LB ให้ retry ไป instance อื่นเมื่อต่อไม่ติด (500 จาก app ยังส่งผ่านไปตามปกติ evidence จึงไม่หาย) ส่วนที่สองให้ verify เช็คซ้ำได้สูงสุด 5 รอบ

LLM ตัวเล็กเขียน root cause กลับด้าน

รอบแรก model เขียนว่า

"... due to a rollback of the payment service to version 1.2.0, which introduced a bug ..."

ทั้งที่ evidence ชี้ชัดว่า v1.3.0 คือตัวที่พัง มันเอา action ที่เราเสนอมาปนกับสาเหตุ วิธีแก้มี 2 ส่วน ส่วนแรกคือเปลี่ยนจากส่ง JSON ดิบให้ model มาส่ง findings เป็นประโยคสั้นๆ และบอกชัดว่ายังไม่ได้ทำ action ส่วนที่สองคือเพิ่ม grounding guard ถ้าคำตอบขัดกับ evidence จะไม่ใช้เลย ถ้าแค่กว้างไปก็เก็บ summary ของ LLM ไว้ แต่เขียน root cause ใหม่จาก evidence ทุกครั้งที่ guard ทำงานจะมีบันทึกให้เห็นใน timeline ของหน้า Problem

AI ทำให้เกิด alert ปลอมกับตัวเอง

LLM รันบน host เดียวกับที่มัน monitor พอวิเคราะห์ทีไร CPU host ก็เกิน 70% แล้วเปิด problem "CPU saturation" ขึ้นมาเอง วิธีแก้คือจำกัด Ollama ไว้ที่ 3 cores และให้ detector ข้าม CPU alert ของ host platform ระหว่างที่ LLM ทำงาน และต่อไปอีก 75 วินาที

ข้อจำกัดและงานต่อ

  • ยังไม่ได้ใส่ Teams webhook ตอนนี้ notification ทุกอันบันทึกเป็น "skipped" ในแอป
  • ยังไม่มี login การ approve ในฐานะ owner ตอนนี้แค่ติ๊กยืนยันว่าเป็น owner ระบบจึงยังบังคับจริงไม่ได้ ถ้าจะบังคับจริงต้องมี SSO หรือ RBAC ที่ผูกคนกับทีม
  • Firewall และ LB ตอนนี้เป็น nginx ที่จำลองขึ้น ของจริงอย่าง Fortinet, Palo Alto หรือ F5 ส่ง syslog มาที่ collector ได้ เพียงแค่ต้องเขียน parser เพิ่ม
  • เป็น single host ถ้า VM ล่มก็ล่มทั้งระบบ รวมถึงตัว monitor เอง
  • LLM บน CPU ช้าตอนเครื่องโหลดสูง ถ้าได้ GPU หรือ API ภายนอกจะเร็วขึ้นมาก
  • ควรเปลี่ยน password ของ sysadmin เพราะเคยถูกแชร์ในแชทไปแล้ว ส่วนการเข้าเครื่องของ agent ใช้ SSH key
